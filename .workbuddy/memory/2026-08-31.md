# 2026-08-31 工作记录

## 网站数据停更的真正原因：Actions cron 派发被平台丢弃

现象：8/31 21:58 网站数据还停在 8/28，**Actions 里没有任何触发记录**
（不是失败，是根本没有 run 被创建）。

排查（判据必须是「有没有 run」而不是「run 成不成功」）：
- `GET /actions/workflows` → `state=active`，工作流没被禁用。
- `GET /actions/runs?event=schedule&per_page=30` → 逐笔算「派发时刻 − 排定 cron」：
  ```
  08-22 ~ 08-26   +10~20 分钟   （正常抖动）
  08-27           +9.5 小时
  08-28           +12.0 小时
  08-29           +4.1 / +3.4 小时
  08-30           +1.1 / +3.8 小时
  08-31 19:37     从未派发（等到 22:00 仍无 run）
  ```
- 已确认**不是**这些常见原因：仓库 public 非 fork、`main` 是默认分支、
  yml 在默认分支上、Actions 未禁用、60 天不活跃未触发、cron 语法合法、
  远端 yml 的 cron 与本地一致（`37 11` / `20 14`）。

**结论：GitHub Actions 的 `schedule` 是 best-effort。**官方文档原文
「The schedule event can be delayed during periods of high loads ...
**In the worst case, the workflow may not run.**」
高负载时排队，队列 TTL 超时后整条派发被**丢弃**——不是延后执行，是不创建 run。
GitHub 社区 discussion #206019（2026-08-26 起大量用户同时报告）证实是平台级现象，
多人观测到 4~10 小时延迟或完全丢弃。19:37/22:20 这种避峰奇数分钟**已经是官方推荐做法**，
仍然挡不住。

**这条要写进认知：cron 没触发不等于配置错了。** 8/28 曾把同类现象归因为
「cron 不可信」，当时判断方向是对的，但缺了「为什么」和「怎么办」。

## 处置：结果导向的看门狗 `tools_gh_watchdog.py`（新建）

判据不是「cron 有没有触发」（不可控），而是「**今天的 data/ 里有没有今天的数据**」。
没有就 `workflow_dispatch` 补跑——这条走实时事件管线，不经批处理 cron 调度器，秒级派发。

- 新鲜度**读远端 raw 不读本地**：本地可能落后远端，用本地判会误以为「没跑」而重复补跑。
- 双探针（`limit_ladder.json` + `digest/latest.json`）：只看一个会误判——
  某接口单独挂掉时另一个仍是新的。
- `_norm_date()` 把三种写法（`20260831` / `2026-08-31` / `2026-08-31 22:05:08`）
  压成 `YYYYMMDD` 再比。**写死单一格式会让「格式不同」被误判成「数据过期」**，
  然后每次都空跑一次补跑——这类误判比漏判更烦人。
- 只判周末不判法定节假日：宁可节假日空跑一次（Actions 免费、脚本内部自己会判无新数据），
  **也不要引一张需年度维护的假日表——过期的假日表会在明年悄悄漏掉整个假期**。
- 退出码 0 就位/已派发、1 非交易日、2 缺失且派发失败、3 用法或凭据错。
- 不 import streamlit（要能在计划任务里跑）；token 从 remote url 解析，不回显。

**反向验证做了三项**（照旧铁律：一条永不失败的断言等于没有断言）：
拿 `20991231` 当目标日必须判 False ✅；三种日期格式归一化 ✅；
8/29 周六 / 8/30 周日 / 8/31 周一的交易日判定 ✅。

### token 解析踩坑

`remote.origin.url` 的形态是 `https://<TOKEN>:x-oauth-basic@github.com/...`
（token 在**用户名**位，不是密码位）。旧的 `sed -n 's#.*://[^:]*:\([^@]*\)@.*#\1#p'`
抠出来的是 `x-oauth-basic`（长度 13），API 一律返 401 Bad credentials。
正确：`sed -n 's#https://\([^:@/]*\):[^@]*@.*#\1#p'`（长度 40）。
**教训：401 Bad credentials 先怀疑「抠错了字段」，别急着怀疑 token 过期或 scope 不够。**
（本次顺带确认 `X-OAuth-Scopes: repo`，与既有认知一致。）

## 已修：绑定失败的归因是编的（8/30 记为待修）

`_supabase_request` 把所有 `HTTPError` 一律吞成 `None`，状态码丢失 → 调用方
只知道「没成功」。于是 `push_binding.py` 的提示写死成一种猜测：
「管理员需执行 `init_wxpusher_column.sql` 补上 `wxpusher_uid` 列」。
但真实最常见的失败是 **409 唯一冲突**（同一微信想绑第二个账号，被
`uniq_users_wxpusher_uid` 部分唯一索引挡住，索引本身是对的）。
后果不是提示不友好，而是**把人指向一个执行完也不会有任何变化的操作**——
管理员照着跑幂等迁移脚本，脚本成功，问题分毫未动。
**归因错误的错误信息比「未知错误」更贵。**

改法：
- `_supabase_request(..., return_error=True)` 返回 `(data, err)`，
  `err = {status, code, message, detail}`（解析 PostgREST 的 JSON 错误体）。
  默认签名不变 → 其余十几处调用方零改动。
- 新增 `explain_uid_write_error(err)` 做翻译：409/`23505`/`duplicate key`/
  索引名 → 「这个微信已绑在另一个账号上，请先去那个账号解绑或换一个微信」；
  `PGRST204` → 才提迁移脚本；`status==0` → 网络；401/403 → 凭据；其余带 HTTP 码兜底。
- 新增 `bind_wxpusher_uid()` 返回 `(ok, why)`，绑定与解绑两处都用它。
  解绑失败的文案改成「绑定仍然有效」——之前写「请稍后重试」，
  用户会以为已经解绑了。
- `update_user_wxpusher_uid()` 保留布尔版，不破坏既有调用。

自检加 5 项（`tools_probe_wxpusher.py` 95 → 97 项）：
前端**不得**再出现 `init_wxpusher_column.sql`（原因必须由 database 按状态码给）、
`bind_wxpusher_uid` 至少被调两次、`explain_*` 里 409/23505/PGRST204 的判定
**必须匹配语法结构**（`re.search(r"status\s*==\s*409")`）而不是裸子串——
注释里正大光明写着「23505 = unique_violation；PostgREST 以 409 透出」，
裸匹配会被自己的注释掩护，把判定分支整个删掉也照样「全部通过」。
反向验证：删掉 409 分支 → 准确报 2 项失败；前端塞回缺列文案 → 报 1 项。
再离线跑 7 个错误样本，7 条分支文案全部命中预期。
