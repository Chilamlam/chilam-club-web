## 行情页沪深撞号修复 + 名称搜索 + 北交所（已推送 `915011f`）

### 起因
用户查「中国稀土」出来「500低贝」。**两处协同失效**：
1. `resolve_symbol` 把所有 `000xxx` 硬编码成沪市（`s.startswith((...,"000","999"))`）；
2. `get_quote` 的另一前缀兜底判据是 `if not q` —— 但沪市指数**未开盘也返回昨收价**
   （`amount=0`、`high/low=0.00`、时间戳停在 09:00:00），有返回 → 兜底永不触发 → 静默出错。

> 教训：兜底条件写「有没有返回」是不够的，必须写「返回的是不是用户要的」。
> 注释里已预见歧义仍然出错，说明**判据选错比没有判据更危险**。

### 关键实测结论（勿再试错）
- 腾讯 `qt.gtimg.cn/q=sh000831,sz000831,bj000831` 一次请求返回多行；不存在的代码
  **整行不出现**（NO-LINE）→ 探三个前缀与探一个网络开销基本相同。
- **请求键必须原样小写**：`usAAPL` 返回 `v_pv_none_match`（不是空行），大小写敏感。
- 活跃度判据：`amount > 0 or (high > 0 and low > 0)`。`sz000806`（银河退，已退市）
  正确判 False。
- **但活跃度不够用**：实测 31 个 `000xxx` 样本里 **21 个沪深两市都在交易**
  （`000001` 上证指数 vs 平安银行、`000063` 上证周期 vs 中兴通讯）。故又叠一层
  `_MAJOR_SH_INDEX` 宽基白名单先验 —— 沪市 000xxx 段全是指数，但会被裸代码主动
  查询的只有上证指数/沪深300/上证50/中证500 这一小撮；其余（500低贝、上证周期、
  全R价值…）用户输入裸 6 位数字的意图必然是同号深市个股。
  `000002` 特意**不**列入（用户输的 000002 几乎总是万科Ａ）。
- **类型判定不能用段位启发式**：`p47/p48`（52周高低）恒为 -1 判指数、`p39`(PE) 空判基金，
  这套在「立讯转债」上错分为基金 → 改成**代码段确定性判定**（110/111/113/118/123/127/128

### 真正的两个口径缺陷（这才是根因）
**A. beta 敞口被算成选股能力。** `alpha = ret - 1.0×bench` 隐含 beta=1，
而 RPS 榜按定义筛的就是高波动小盘成长股。以入选日为观测单位 OLS：
**beta≈3.75（R²=0.56，相关 +0.746）**，截距 -2.79%/5日。
beta 校正后超额中位数从 **-3.61% 收敛到 -1.79%**；独立窗口口径 **-0.83%、胜率 50.0%**。
逐窗口看更清楚：20260817 原始 alpha -6.45%，beta 调整后 **+3.89%**（那周基准跌 3.75%）。
→ 高 beta 组合在跌市里的放大跌幅，1:1 减法会整笔记到「选股能力」头上。

**B. 样本量虚高一到两个数量级。** n=2210 里含 T+5 重叠窗口（相邻日共享 4 天持有期）
+ 同日 60 只截面高相关。折算不重叠窗口只有 **8 个**，3 胜 5 负，
**双侧精确二项检验 p=0.727**，无法拒绝「胜率=50%」；t=-0.90，95%CI [-13.7%, +6.1%] 跨 0。
日间波动/日内波动 = 0.87。
→ 「稳定反向超额」这个说法本身就不成立，样本还不够judge方向。

## 任务三：定位并绕过 `CONNECT tunnel failed, response 502`（收尾）

记忆 commit `85852cf` 连续 3 次 push 全部 502，先走 API 兜底通道落地远端
（新 head `39e3f18`，两文件 blob sha 与本地 LF 归一化后逐一相同，tree 与本地
`85852cf^{tree}` 同为 `c0749062`），再回头定位根因。

### 根因
`HTTP_PROXY / HTTPS_PROXY / http_proxy / https_proxy` 全部指向 `http://127.0.0.1:63726`
——**本机代理端口已失效**。curl 走系统栈不吃这套环境变量，所以呈现「API curl 全绿、
git 全 502」的分裂现象，很容易误判成 GitHub 侧故障或网络抖动。

### 验证与解法
```bash
env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy \
  git -c http.proxy= -c https.proxy= -c http.version=HTTP/1.1 fetch origin main
```
一次成功（`* [new branch] main -> origin/main`）；`ls-remote` 与 `push --dry-run`
同样通过。`-c` 与 `-u` 必须同时给：git 会同时读环境变量和自身 config。
502 是**确定性失败**，重试循环无意义。

顺带修掉一个自己写的坑：`if git push 2>&1 | tail -2; then break; fi` 的退出码取
`tail`（恒 0）→ 首次即 break，看着是重试三次实际只跑一次。

### 本机 ref 老问题复现
`fetch` 报成功但 `git rev-parse origin/main` 仍 `unknown revision`，
`.git/refs/remotes/origin/` 目录压根不存在。按 MEMORY 既有做法手写
`.git/refs/remotes/origin/main`，`for-each-ref` 复核通过后
`git reset --mixed 39e3f18` 对齐（tree 相同故工作区零变化）。
对齐后 `tools_probe_scorecard.py` + `tools_probe_scorecard_ui.py` 复跑全绿。

## 【重大纠正】本机 `env` 是个静默吞命令的壳 —— 我报的「PUSH_OK」是假的

推送本轮 commit 时，`env -u HTTP_PROXY ... git push origin main` 一次就打印了 `PUSH_OK`。
但随后 API 查远端 HEAD 仍是 `c1bc290`。起初怀疑是 API 缓存，加 cache-buster、
改用 `ls-remote` 复查 —— `ls-remote` **零输出、退出码 0**。这才是线索：
真 git 无论成败都有输出，「零输出 + exit 0」意味着 git 根本没被执行。

根因：`PATH` 里 `~/.local/bin/env` 排在 `/usr/bin/env` 之前（`type -a env` 可见三个），
而那个文件是 Aug 20 落下的 sh 脚本，内容只是「若 PATH 未含 ~/.local/bin 就追加」，
**完全忽略自己收到的参数**。所以 `env -u X git push ...` 等于跑了个空脚本然后 exit 0。

对照实验（决定性）：
- `/c/Users/Lenovo/.local/bin/env -u HTTP_PROXY git push origin main` → 零输出，exit 0
- `/usr/bin/env -u HTTP_PROXY git ls-remote origin main` → 正常返回 `c1bc290 refs/heads/main`

**这条影响的不只是本轮**：MEMORY 里那条「解法 `env -u HTTP_PROXY ... git`」是 09-01 写的，
此壳当时已存在 → **早前所有「用 env -u 绕代理后 git 成功」的记录都不可信**，
那些「成功」很可能只是这个壳在静默返回 0。以后判断推送是否真成功，
**只认远端 sha**，不认命令退出码。已把这条写进 MEMORY「Git/部署」段首位。

顺带查清当前真实网络状况（与旧的代理 502 无关）：
- 代理变量 `HTTP_PROXY`/`HTTPS_PROXY`/`no_proxy` **全为空**，已不需要绕代理；
- `github.com:443` **间歇不可达**（curl 三次一成，失败是 21s 超时 `curl 28`）；
- `api.github.com` **稳定 200**（0.34s）。
→ 即 git 传输通道不可靠而 REST API 可用，**推送应直接走 API 兜底**，
反复重试 push 是浪费（实测 5 次仅第 1 次连上、且那次是 `remote end hung up`）。

最终推送：`tools_gh_put_via_gitdata.py --msg "$(git log -1 --format=%B babb50f)" <6 个文件>`
→ 远端新 HEAD `f17a616`，parent `c1bc290`，**tree `f6239115619a` 与本地 babb50f 的 tree 完全一致**，

### 1. 推翻自己前一版的解释：末根丢失**不是**「顶满 limit 才丢」

前一版 docstring 我写的是「区间根数顶满 limit 时会少给最新一根」。**这个解释是错的**，
用三个临时脚本钉死了真实规律：

- `_tail_rule.py`（扫 start × limit × `end=今天` 矩阵）：`start=2026-06-01` 总共才 **66 根**、
  远没顶满 limit，但 `limit=200` 丢当天、`400` 给、`800` 又丢 —— **非单调**，
  「顶满才丢」直接被否证。
- `_tail_rule2.py`（同参数连打 4 次）：结果**完全一致**，不是网络抖动，是服务端行为。
- `_tail_limit.py`（6 标的 × 3 start × 5 limit = 90 次）：含当天比例
  **L300 18/18、L100 17/18、L800 13/18、L640 只有 10/18**。
  且**任何分片都只会少给最新一根、从不多给** —— 各分片取 max 就是真实最新交易日
  （6 个标的复核全部 == 当天）。

真实机制：服务端按 `(code, start, end, limit)` **分片缓存**，`end=当天` 时部分分片当天还没刷新。
→ 所以补尾逻辑不猜规则、只看实得：`if merged and max(merged) < end: _pull(max(merged), end)`
