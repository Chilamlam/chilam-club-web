## 修复方案与 A/B 反向验证（`shell_ab.py`）
把壳页 iframe 的 src 从 `…/?embed=true` 改为 **`…/~/+/?embed=true`**（跳过包装页）。
同一套浏览器、同一套判据，量测两份真实 index.html：

| 视口 | OLD（线上现状） | NEW（修复版） |
|---|---|---|

| mobile 390×844 | **FAIL** 同样 150px | **PASS** 铺满 844px、md=192、文字 3424 |
| 第三方 Cookie 限制开（模拟隐私模式，实测拦下 9~11 个 Cookie） | **FAIL** 仅 34 字 | **PASS** 900px、md=192 |

判据设计（防假断言）：
- **元断言**：必须真的出现跨站 iframe（OOPIF），否则报 NOTHING 而不是 PASS；
  Cookie 组必须真的观测到 `blockedCookies>0`，否则「限制未生效，本次什么都没验到」。
- **高度阈值**：app 高度须 ≥ 视口 80%，否则算「被钳制」——只判 hasApp 会被 150px 蒙过去。
- **A/B 双向**：OLD 若也 PASS 则判据抓不住白屏（假断言），结论作废；NEW 若不 PASS 禁止上线。
- **造错反验**（`fix_verify.py`）：
  - `Z_broken` 不存在的 host → 落到 `share.streamlit.io/errors/not_found`，0 字，FAIL ✔
  - `Z2_wrongsite` example.com → 真的产生 OOPIF 且有 129 字，但 hasApp=False，FAIL ✔
    （证明判据不会被「无关内容」喂饱）
- **判据放宽后复验**：为容纳官方旧版 app（无 `stMarkdown` testid）把判据放宽成
  `md>20 或 textLen>500`，放宽后重跑造错组仍全 FAIL，才敢用。
- **横向验证 `/~/+/` 是平台通用能力**：官方 `30days.streamlit.app/~/+/?embed=true`
  同样 PASS（1013 字）→ 不是本站私有实现，方案可上线。

**残留风险（已如实记录）**：`/~/+/` 是 Streamlit Cloud 内部路径、非公开 API，
平台若再改会二次失效。彻底免疫的做法是壳页 302 跳到 `chilam-club-app.streamlit.app`
（代价：地址栏不再是自有域名）。

## 数据停更事故：根因是 cron 派发被丢弃，不是延迟（`sched_lag2.py`）
用户报障时刻 09-02 22:55 CST（14:55 UTC），当时**最后一次成功完成的定时跑批是
20.7 小时前的 #342（09-01 18:11 UTC）** → 用户看到 09-01 数据，如实反映当时状态。

诚实性修正：GitHub API 的 run 对象**不暴露是哪条 cron 触发的**，
第一版脚本按「最近计划时刻」硬归因，延迟数小时时会张冠李戴（把 11:37 延迟 4h
误判成 14:20 的班），得出「主班自 08-26 起失灵」这种不可靠结论。改成只报可证事实：
**计划 72 条 / 实际 40 条 → 至少丢弃 32 条（44%）**，这是不依赖归因的下界。

延迟分布（每日最早 run 相对 11:37 UTC）：
```
07-29 ~ 08-26   +0.2h ~ +2.3h   正常抖动
08-27           +9.5h   ← 拥塞骤然恶化
08-28          +12.0h
08-29 ~ 09-02   +3.6h ~ +6.5h   持续劣化，且多数日子当天只产生 1 条派发
```
即 `schedule` 是 best-effort，**高负载时整条派发被丢弃**（不是延后执行），
被丢时无邮件、不进状态页、Actions 列表无痕迹 → 表现为「数据停更且看不到失败记录」。
`tools_gh_watchdog.py` 的注释里已经写明这一点，判据是结果导向（今天 data/ 有没有今天数据），
**但它没有被任何东西定时调用**——这是本次事故真正的缺口。

远端 data/ 现状复核（`data_fresh.py`，读文件内日期字段而非 commit 时间）：
`strong_stocks/strong_etfs/breakout_stocks/market_sentiment/limit_ladder/
speculation_data/ai_market_analysis` 全部 = 2026-09-02，`index_history.csv` 尾行 09-02，全批一致。

### 新踩的坑：日期正则会把非日期数字认成日期
`data_fresh.py` 把 `index_history.csv` 判成「最新 2027-10-27」，实际文件里
最大日期是 09-02——`20271027` 是别的字段（疑似 ID）被 `(20\d{2})(\d{2})(\d{2})` 误匹配。
