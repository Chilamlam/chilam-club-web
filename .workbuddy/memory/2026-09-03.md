### 修掉的缺陷 ①：取不到 ≠ 数据旧（拿测量工具的故障当被测对象的故障）

实测现场：`tools_gh_watchdog.py --check` 跑了 **4m13s**，四个产物全 `HTTP=0`，
报「今日数据缺失」；**同一时刻 curl 落盘四个全 200**，读数都是 20260902。
旧版把 `HTTP=0` 直接算进 `ok=False`，于是**通道一抖就在默认模式下派发一次
12~18 分钟的全量补跑**。这正是记忆里那条「测量工具自己会骗人」的同型复发。

改法：`check_freshness` 返回**三态而非布尔** —— `fresh` / `stale` / `blind`。
- 主通道换成 **curl 落盘再读**（`-o /dev/null` 在本机会假报 exit=23/size=0，绝不用它判成败），
  urllib 退为备用；`fetch_remote()` 双通道串联。
- 一个产物都没读出日期 → `blind`、**退出码 9**、**绝不派发**，输出明说「什么都没验到」。
- 取到了但解析失败（列改名）→ 算 `stale` 而非 `blind`（文件在、内容不对，是真问题）。
- 只验到一个且是今天的 → 仍是 `stale`，不能报 fresh（其余三个未验证）。

### 修掉的缺陷 ②：跑批前「今天没有今天的数据」是正常态

10:07 去查必然查不到当日数据，旧版报「缺失」。若挂成每小时一次，整个白天都在空派，
而收盘前派发的跑批因行情未发布只会把昨天数据再写一遍（见
`daily_breakout.get_latest_trade_date` 的锚定规则）——纯烧 Actions 额度。
加 `judge_after()` = **主 cron + RUNTIME_MIN + JUDGE_MARGIN_MIN 三常量联动**
（改 cron 不会漏改判定线），早于判定线直接 return 1 且**不发起远端检查**（元断言守着）。

### 修掉的缺陷 ③：派发成功 ≠ 已修复

旧版派发成功返回 0，于是「今天很太平」与「今天出过事、修复结果无人复核」共用一个信号。
2026-09-01 的 RPS 正是这种形状：派发成功、退出码 0，数据依旧停在前一天。
新增**退出码 4 =「已派发、结果未验证」**，并由 23:10 那班复核兜底。

退出码全表：0 就位 / 1 无需跑批 / 2 确实缺失或派发失败 / 3 凭据问题 / 4 已派发未验证 / 9 什么都没验到。

配套 `tools_probe_gh_watchdog.py`：正向 **47/47**（含真联网 + 带外 curl 交叉复核 + 404 不当数据），
反向 **9/9 造错全抓**。所有会走到派发分支的用例都把 `dispatch` 换成计数器并断言次数
——探针本身绝不触发真跑批。

## 本轮反向验证踩的三个新坑（已写进 skill）

1. **等价改动 = 造错没造**：把 `minutes=RUNTIME_MIN + JUDGE_MARGIN_MIN` 造成 `minutes=53`，
   而 18+35 恰好 53 → 行为逐位相同，任何断言都抓不住。改成 90 才有区分度。
2. **`expect` 必须在失败行里命中，不能在全量输出里命中**：`ck(cond,msg)` 无论成败都打印同一句
   msg → 「别的断言挂了」+「msg 出现在某条 PASS 行」会被算成 caught。
   过滤时先取 `[FAIL]` 行与末尾清单行。
3. **期望关键字要取失败分支才会打印的文案**：`try: f(); bad("必须抛错") except: ck(True,"带列名")`
   造错后走 `bad()`，关键字写「带列名」永远命中不了。
