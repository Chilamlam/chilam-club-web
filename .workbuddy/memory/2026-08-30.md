## 工作流「薄壳化」——彻底解决每次改 yml 都要人工介入（本日第二项）

新增 `run_daily.py`（编排器，普通 .py 可自由推送），yml 从 16 步砍到 5 步：

下沉到 `run_daily.py` 的内容：
- `STEPS` 步骤表（11 个跑批脚本）：顺序即依赖顺序，含 key/script/label/backfill 模式/timeout

## 付费用户邮件投递：查出两个「静默失败」的致命 bug
用户问「怎样让付费订阅用户也收到信息」。核查后发现链路根本走不通，且两处都不报错：

1. **`daily_digest.subscriber_emails()` 读了不存在的列**。写的是
   `s.get("end_date") or s.get("expire_date")`，而 `subscriptions` 表实际列名是

   日志只平静打印「有效订阅用户 0 位」，看起来像"确实没人订阅"。
   **字段名写错的取数逻辑不抛异常，只给出语法正确、语义为空的答案**，这类静默失败最难发现。
   已修 + 加 status=active 过滤 + 表结构不符时显式报错（而非返回 0 位）+ 尊重 `digest_optin`。

### 待修：同微信绑第二个账号会报错，且错误归因是错的

`init_wxpusher_column.sql` 建了部分唯一索引 `uniq_users_wxpusher_uid`（同一微信不许绑多账号，
设计本身正确）。但 `push_binding.py:141` 写库失败时的提示写死为
「管理员需执行 init_wxpusher_column.sql 补上 wxpusher_uid 列」——
**这是把「唯一冲突 409」误报成「缺列 PGRST204」**。
根因：`_supabase_request` 把所有 HTTPError 一律吞成 `None`，
`update_user_wxpusher_uid` 只能返回布尔，状态码丢失 → 上层无法区分失败原因。
后果：自己用同一个微信测第二个账号时，会看到一条把人引向错误方向的提示
（去 SQL 里加已经存在的列）。修法：让 `_supabase_request` 或
`update_user_wxpusher_uid` 透出状态码/错误体，409 单独提示「这个微信已绑在别的账号上，
请先在原账号解绑」。**这是「静默失败」的变种：失败被如实上报了，但归因是编的。**

**由此产生的验证顺序约束**：管理员微信是下单告警的唯一收件人
（`get_admin_wxpusher_uids()`）。若为测绑定而先在管理员账号解绑，告警通道同时失效。
正确顺序：先验下单告警 → 再验确认收款/VIP 激活 → 绑定环节用第二个微信，
没有第二个微信就放在最后测。

### 已修：后台管理页 `switch_page` 从上线起就是坏的

现象：点侧边栏「⚙️ 后台管理」→ `StreamlitAPIException`（Cloud 上详情被脱敏，
只剩一个没有信息量的红框）。栈顶是 `app.py:668 st.switch_page("admin.py")`。
根因：**`admin.py` 在仓库根目录**。Streamlit 的 pages/ 多页架构只把
「入口脚本 + `pages/` 目录下的文件」注册成页面，根目录其它 `.py` 只是普通模块。
源码判定：`matched_pages = [p for p in all_app_pages if p["script_path"] == requested_page]`
为空即抛「Only the main app file and files in the `pages/` directory are supported」。
`git log --diff-filter=A -- pages/admin.py` 为空 → **这个按钮从加进来那天起就没能用过**，
只是此前一直没人点（订单确认此前都在本地/API 侧验证）。
修法：`git mv admin.py pages/admin.py`，`app.py` 改 `st.switch_page("pages/admin.py")`。
搬家后 `sql_path` 必须改成 `os.path.join(_ROOT, "init_payments_table.sql")`
（相对路径在子页目录下会失效），并补 `sys.path` 引导（与 `pages/dashboard.py` 一致）。
文件头写死「不要再搬回根目录」的位置约束。

**自检加固 `tools_check_st_api.py`**：新增 switch_page/page_link 目标校验——
非 `app.py` 且非 `pages/` 前缀 → 报「不是已注册页面」；`pages/` 前缀但文件不存在 → 报「指向的文件不存在」；
`http(s)://` 放过（page_link 允许外链）。这类错误**静态完全可判定**，不该留到线上。

**踩坑（顺序 bug，值得记）**：新断言首版放在原有
「签名含 `**kwargs` 就 `continue`」之后 → 永远走不到。反向测试（造一个含
`switch_page("admin.py")` 的假仓库）报 0 项才发现。教训：
**一条永不失败的断言等于没有断言，加完必须造错反向验证一次**。
（本次 1.62 实测 `switch_page` 签名是 `(page, query_params)` 未被装饰器吞掉，
但顺序仍应前置——不能依赖某个版本的装饰器行为。）
另一坑：反向测试目录别用 `/tmp/...`，Windows 下 Python 解析成 `\tmp\...` 找不到，
`rglob` 扫到 0 个文件同样显示「全部通过」。改用 `C:/Users/Lenovo/wb_negtest` 才真跑起来。

副作用备查：`pages/` 下的文件会自动出现在默认侧边栏导航（`client.showSidebarNavigation`
默认 True），所以「admin」这一项对所有访客可见。`pages/admin.py` 开头的
`is_logged_in` + `is_admin` 双重校验是真正的门禁，不能删。

### push 被 rejected 的正确读法（不是传输故障）

`push` 连试 6 次全 `! [rejected] main -> main (fetch first)` ——
**这是服务端的答案，不是网络问题**，重试一百次也是同一结果。
根因：跑批在此期间提交了两笔 `Auto-update daily data`（`c0ad035`/`ddc5770`），
远端已领先。处置：`fetch` → 确认远端两笔只动 `data/`（与本轮改动零重叠）→
`git rebase origin/main` → 再 push，一次成功。
**教训：`rejected (fetch first)` 和「传输挂死无输出」是两类完全不同的失败，
前者要 fetch+rebase，后者才需要重试/换 HTTP/1.1/走 API 兜底。**
`data/` 归 Actions 所有，所以本地推之前永远先 fetch --rebase（旧铁律再次生效）。

远端核验：`a38ae0b`；`contents/admin.py` 返 404（根目录那份确实没了），
`contents/pages` = admin.py / auth.py / dashboard.py。
