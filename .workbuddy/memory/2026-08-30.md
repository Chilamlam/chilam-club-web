## 本轮发现并修复的两个真实 bug

**1. 战绩百分比漏乘 100（严重误导）**
线上摘要写「RPS 强势榜：5日超额中位数 **-0.04%**」。用 `picks.csv`(2460行) + 
`prices.csv`(9068行) 独立复算得 `n=2092 median=-0.038161`，与 `performance.json` 完全吻合
——**计算层没错，只有展示层错**。根因：`digest.py` 直接 `{h['alpha_median']:+.2f}%`，
而 `alpha_median` 在 `scorecard.py` 里是 `float(a.median())` 存的小数。
教训：**战绩数字报小 100 倍比报大更危险**，它会让一个明显失效的榜单看起来「几乎打平」。

**2. 测试 fixture 单位与生产不一致，使上述 bug 隐形**
`tools_probe_digest.py` fixture 写 `alpha_median: 0.83`（本意 0.83%），断言
`"+0.83%" in md` 恰好通过，76 项断言全绿却放过了漏乘。改为 `0.0083`，
断言不变但语义变成「必须乘 100」。

**3. 区分度结论未进摘要**（设计缺失，非代码错）
`performance.json` 明确有 `monotonic: false` + `verdict: 排序未通过单调性检验…`，
但摘要只报中位数。补 `⚠️` 行——这个难看的结果按「事后对账」的设计恰恰要主动公示。

**4. 情绪派生永久 `insufficient`**
`derived.json` `status=incomplete`、`phase.status=insufficient`，
查 `ladder_history.csv` 只有 1 天（20260828，82 行）、`breadth_history.csv` 1 行。
根因：`daily_scorecard.py` 有 `--backfill`，`daily_sentiment.py` **没有**，
40 天回溯只覆盖战绩不覆盖情绪。
修复：实测东财涨停池接口 `date` 参数**可回溯约 15 个交易日**（8/10 起有数据，
8/07 及更早 `tc=0`），给 `daily_sentiment.py` 加 `fetch_ladder_remote` + `backfill` + 
`--backfill` 入口，工作流 `Run Sentiment Derived` 接入 `backfill_days`（自动截顶 15）。
回溯只补涨停池 + 全市场涨幅（收盘即固化的客观事实），刻意不复用三通道兜底

## 工作流「薄壳化」——彻底解决每次改 yml 都要人工介入（本日第二项）

用户诉求：不想每次新增跑批/改顺序/加 secret 都手动去网页端粘 yml。
**PAT 拿不到 workflow scope 是既定约束，正解不是要更大权限，而是让 yml 不再承载会变的东西。**

新增 `run_daily.py`（编排器，普通 .py 可自由推送），yml 从 16 步砍到 5 步：
Checkout / Set up Python / Install deps / **Run daily pipeline** / Commit and push。

下沉到 `run_daily.py` 的内容：
- `STEPS` 步骤表（11 个跑批脚本）：顺序即依赖顺序，含 key/script/label/backfill 模式/timeout
- 三种回溯模式：`none` / `inline`（带 --backfill 跑一趟）/ `extra_pass`（先回溯再当日增量两趟）
- `backfill_cap`：sentiment 截顶 15（东财接口能力），scorecard 无上限
- `FRESHNESS` 数据新鲜度自检表（原先写在 yml 里）
- 失败语义：逐步骤捕获异常/非零码后继续，**编排器恒 exit 0**（否则 yml 的 data/ 提交步骤不执行）
- 每步独立 timeout，超时记 124 后继续（单脚本挂死不能吃掉整个 job）
- `--only a,b` 只跑指定步骤、`--list` 只打印步骤表（调试用）

**secrets 改 `ALL_SECRETS: ${{ toJSON(secrets) }}` 整体透传**，`inject_secrets()` 展开成环境变量。
这是「新增 secret 不必改 yml」的关键——以后加 `DIGEST_SERVERCHAN_KEY` 只需在 Secrets 页面添加。
细节：空值不注入（未配置的渠道不能被误认为已配置）、跳过 GITHUB_TOKEN、
已存在的环境变量不覆盖（本地调试可顶替）、从 environ **pop** 掉避免子进程拿到明文全集、
只回显键名绝不回显值。

**yml 里手动输入一律走 env 不直接插值**：`inputs.only` 拼进 run 脚本等于命令注入
（输入带引号/分号即可逃逸），改为 `ONLY_STEPS` env 后 shell 只当普通字符串。

新增 `requirements-batch.txt`（跑批依赖与前端 `requirements.txt` 分开：
前端的 streamlit 跑批不需要，跑批的 lxml/bs4/cloudscraper 前端不需要）。
「加一个依赖」是最常见变更之一，放普通文件才能自由推送。

新增 `tools_probe_run_daily.py`（68 项，纯离线不跑真实脚本）。断言重点是**编排语义不许退化**：
步骤脚本必须真实存在、**仓库里所有 `daily_*.py` 必须全部进入步骤表**（防新增跑批忘挂）、
顺序依赖成立、原 yml 的 11 步全覆盖（防薄壳化漏搬）、回溯截顶正确、

  而域名拼错则表现成网络错误——两种都会把排查方向带偏到「key 复制错了/网络问题」。
  已在 `daily_digest.py` 加 `_serverchan_url()` 按前缀自动分流，自检加 4 条断言
  （含三组端点映射的实际调用断言）。`tools_probe_digest.py` 现 92 项全通过。
- **`python urllib` 在本机会被 TLS 打断**（`SSL: UNEXPECTED_EOF_WHILE_READING`），
  同一 URL `curl` 稳定 200。这与 git 的 HTTP/2 问题是两回事，且 `curl 200` 也不代表
  urllib 通。已给 `tools_gh_put_via_gitdata.py` 的 `_req` 加 curl 兜底：
  **只在传输层异常时兜底，HTTPError（404/422）不兜底**——那是服务端的答案，
  重发只会得到同样结果，还可能把非幂等 POST 重复执行一次。
